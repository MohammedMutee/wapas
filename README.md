# Wapas — revenue that came back

**Razorpay AI Buildathon · Track 03 · AI Revenue Recovery**

An agent that detects revenue at risk, diagnoses why it is at risk, executes a
bounded recovery workflow under deterministic guardrails, and **proves in rupees
what it recovered against a control group it never touched.**

### Where the accuracy comes from, and where the model earns its place

Diagnosis is three problems, so it is measured as three — both classifiers over
the **same 5,000 episodes**, because accuracy is not a causal question and does
not need randomised arms. Both are given the merchant's resolved history;
denying a baseline that would be a strawman.

| | model | keyword classifier | single-episode ceiling |
|---|---|---|---|
| Wording seen in history (65%) | 100% | 100% | 100% |
| **Wording never seen (18%)** | **94.2%** | **67.8%** | 100% |
| Text identifies nothing (17%) | 50.7% | 50.7% | 44.5% |
| **Overall** | **90.5%** | 85.6% | 90.5% |

**The model is consulted on 17% of episodes.** A wording resolved before is
answered by lookup. Text that identifies nothing is answered by an outage
detector or by base rates. Both are optimal on their own ground and both are
free — routing everything through a model because it is the interesting
component would be worse on the metric and worse on the bill.

What is left is the column where a keyword table falls off a cliff: the first
time an acquirer rewords a decline. **68% against 94%.** That is the whole case
for a model here, and the keyword table is **frozen** against those wordings —
no keyword may ever be added for them, and git history makes that checkable.

The no-signal row beats its own ceiling because the system stops reading one
episode at a time: forty failures on one bank inside an hour is an outage, and
that is evidence this payment's error text does not contain.

## Why a control group

A large share of failed payments recover on their own — the customer simply
tries again. Any system reporting *gross* recovery is claiming credit for
customers it never touched.

Wapas randomly assigns 15% of episodes to a **control arm that receives no
treatment at all**, and reports the difference. The headline metric is
**net incremental recovery**: what the agent recovered beyond self-recovery,
minus every rupee it spent on channels and tokens to get there.

Assignment is stratified by amount decile, the decision rule is a stratified
permutation test, and the report publishes a **placebo comparison** — one arm
split in two — beside every real claim, so a reader can see what the harness
reports when there is nothing to report. `make calibrate` measures the
false-positive rate over hundreds of known nulls rather than assuming it.

## Run it

```bash
make install     # venv + dependencies
make up          # Postgres + Redis via docker compose
make migrate     # schema
make test        # unit + property tests
make warm        # pre-fetch every distinct diagnosis prompt into .cache/
make eval        # seeded batch, rules planner → results/report.md
make eval-llm    # same, with the LLM agent as the treatment arm
make calibrate   # false-positive rate on known nulls → results/calibration.md
make sweep       # ±30% on every parameter → results/sensitivity.md
make redteam     # 33 adversarial scenarios; expect 0 escapes
make demo        # one real episode end-to-end against Razorpay test mode
make dashboard   # render the results into results/dashboard.html
make secrets     # scan the tree and full git history for credentials
```

## Architecture in one line

**The LLM proposes; deterministic code disposes.** A language model can be
persuaded; a policy engine cannot. Every action passes schema validation and
then a policy gate written in plain Python with no prompt and no context
window. That separation is why the red-team result can be a number rather than
an impression.

See [`ARCHITECTURE.md`](ARCHITECTURE.md).

## Honest limitations

- **Metrics are simulator-produced.** The generative parameters live in
  `sim/params.yaml` and are published. The agent never sees them. A sensitivity
  sweep perturbs every parameter ±30% to show the result is not parameter-tuned.
- **Compliance rules are an engineering model, not legal advice.** Every rule in
  `policies/*.yaml` carries `source` and `verified`. Rules with
  `verified: false` have not been independently confirmed and are not presented
  as regulatory citations. See [`docs/compliance.md`](docs/compliance.md).
- **Test mode only.** No live-mode code path exists in this repository. The
  configuration loader refuses to start with a key beginning `rzp_live_`.
- **Checkout abandonment is deliberately out of scope.** Reasoning in
  [`docs/scope.md`](docs/scope.md).
